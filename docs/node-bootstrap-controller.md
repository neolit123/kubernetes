# Node Bootstrap Controller — Design Proposal

## Overview

This document proposes a new external controller that provides verified node bootstrapping
for Kubernetes clusters without requiring changes to core Kubernetes components.

The controller addresses a gap in the existing bootstrap token model: bootstrap tokens
prove nothing about the node presenting them. Any machine that obtains a token can use it
to join the cluster. This controller closes that gap by independently verifying a node's
identity and software measurements before admitting it.

## Motivation

The existing bootstrap token workflow:

1. Admin generates a token (`kubeadm token create`)
2. Token is distributed to the joining node
3. Node uses the token to authenticate and submit a CSR
4. The built-in CSR approver approves it based on the token group alone

Problems:
- A stolen or intercepted token can be used from any machine
- The cluster has no record of which nodes are expected to join
- There is no verification that the node is running expected software
- Certificate rotation (every 24h) re-uses the same credentials with no re-verification

## Design Goals

- No changes to the Kubernetes apiserver, KCM, kubelet, or scheduler
- Single controller binary handles both the provisioning and CSR approval
- Single CRD tracks the full node lifecycle from intent to joined
- Works alongside CAPI, cloud-init, bare-metal provisioners — agnostic to VM creation
- SSH credentials are image-wide (not per-node), so no per-node secret distribution
- The controller, not the node, generates the keypair — node cannot fake its measurement results

## Non-Goals

- Not a replacement for hardware attestation (TPM, cloud identity)
- Not a VM lifecycle manager (does not create or destroy VMs)
- Not a replacement for CAPI in environments that already use it
- Does not require control-plane → node network paths for anything except SSH at join time

## Architecture

```
Admin creates NodeJoinRequest CR
         │
         ▼
Controller Loop 1: Provisioning Reconciler
  - Polls node IP via SSH until reachable
  - Verifies measurements directly over SSH (not self-reported)
  - Generates ECDSA P-256 keypair
  - Writes private key to node at /var/lib/kubelet/pki/node-identity.key
  - Writes bootstrap-kubelet.conf to node at /etc/kubernetes/bootstrap-kubelet.conf
  - Records public key in NodeJoinRequest.status.publicKey
  - Updates NodeJoinRequest.status.phase = Verified
         │
         ▼
Node: kubeadm join (polling for bootstrap-kubelet.conf)
  - Detects file appeared, proceeds with TLS bootstrap
  - kubelet submits CSR using pre-generated keypair
         │
         ▼
Controller Loop 2: CSR Approval Reconciler
  - Watches CertificateSigningRequests for signer kubernetes.io/kube-apiserver-client-kubelet
  - Extracts node name from CSR subject (system:node:<name>)
  - Finds NodeJoinRequest named <name>
  - Compares public key in CSR against NodeJoinRequest.status.publicKey
  - Approves if match, denies otherwise
  - Updates NodeJoinRequest.status.phase = Joined
```

## The NodeJoinRequest CRD

```yaml
apiVersion: bootstrap.kubernetes.io/v1alpha1
kind: NodeJoinRequest
metadata:
  name: worker-1          # must match the node name the node will register with
spec:
  # nodeIP is the IP address the controller will SSH to.
  nodeIP: 10.0.1.5

  # bootstrapExpiry is the deadline for the node to complete its first join.
  # If the node has not joined by this time the request is marked Expired
  # and the controller will not approve any CSRs for this node.
  # +optional
  bootstrapExpiry: 24h

  # expectedMeasurements constrains what must be running on the node.
  # Verified by the controller over SSH — not self-reported by the node.
  # +optional
  expectedMeasurements:
    # kubeletHash is the SHA-256 hex digest of /usr/bin/kubelet (or the path
    # configured in the node image). If set, the controller rejects nodes
    # where the binary hash does not match.
    # +optional
    kubeletHash: ""

    # osImageID is matched against /etc/os-release IMAGE_ID or ID.
    # +optional
    osImageID: ""

    # kernelVersion is matched against /proc/version.
    # +optional
    kernelVersion: ""

status:
  # phase tracks the lifecycle of this join request.
  # Pending:   CR created, controller has not yet verified the node.
  # Verified:  Controller SSHed to node, verified measurements, wrote credentials.
  # Joined:    Node's CSR was approved; node is a cluster member.
  # Expired:   bootstrapExpiry passed before the node joined.
  # Failed:    Measurement mismatch or SSH error; node was rejected.
  phase: Pending

  # publicKey is the PEM-encoded ECDSA public key generated by the controller
  # and written to the node. Set after phase transitions to Verified.
  # The CSR approval loop verifies the CSR's public key matches this value.
  publicKey: ""

  # verifiedAt is the time the controller completed SSH verification.
  # +optional
  verifiedAt: null

  # joinedAt is the time the node's CSR was approved.
  # +optional
  joinedAt: null

  # failureReason contains a human-readable description of why the request failed.
  # +optional
  failureReason: ""

  # conditions holds detailed status conditions.
  conditions: []
```

## SSH Credentials

The controller uses an **SSH Certificate Authority** model. No SSH private keys
are ever distributed to nodes or transmitted over the network.

### Why SSH CA instead of static keys

**Standard SSH without a CA** requires each machine to maintain an
`authorized_keys` file listing every specific public key allowed to connect.
At cluster scale this means thousands of files to synchronise — and every key
is a long-lived credential that grants access indefinitely if stolen.

**With an SSH CA**, each node only needs one line in `sshd_config`:

```
TrustedUserCAKeys /etc/ssh/controller-ca.pub
```

The node trusts *certificates* signed by that CA, not specific keys. The
controller issues short-lived certificates on demand and discards the session
key immediately after use. There are no long-lived credentials to steal, no
per-node key files to manage, and no key distribution problem.

This is the same model as HTTPS — your browser doesn't list every valid server
certificate; it trusts a set of CAs and accepts any certificate those CAs have
signed. The controller is the CA for its own SSH sessions.

### How it works

The controller holds one SSH CA private key (generated in memory at startup —
see Deployment section). Every node image ships with a single trusted CA public
key in `sshd_config` (fetched from `kube-public` at cloud-init time).

When the controller needs to SSH into a node:

1. **Generate** a fresh ephemeral ECDSA keypair entirely in memory — never
   written to disk or stored anywhere
2. **Issue** a certificate by signing the ephemeral public key with the CA key.
   The certificate encodes:
   - **Principal:** `root` — the Unix user allowed to authenticate with this cert
   - **Valid after:** now
   - **Valid before:** now + 10 minutes — hard expiry, sshd rejects after this
   - **source-address:** controller Pod's IP — sshd rejects connections from any
     other IP even if the certificate and key are valid
   - **Serial number:** unique per certificate — logged by sshd for audit
3. **Connect** to the node using the ephemeral private key + certificate
4. **Verify** measurements, write bootstrap credential files
5. **Discard** the ephemeral keypair — it exists nowhere after the session ends

### Certificate structure

An issued certificate looks like:

```
Type: ecdsa-sha2-nistp256-cert-v01@openssh.com user certificate
Public key: ECDSA-CERT SHA256:<ephemeral-key-fingerprint>
Signing CA: ECDSA SHA256:<ca-key-fingerprint>
Key ID: "node-bootstrap/worker-1/2026-05-07T10:01:00Z"
Serial: 42
Valid: from 2026-05-07T10:01:00 to 2026-05-07T10:11:00
Principals: root
source-address: 10.96.0.5/32
```

The `Key ID` and serial number are logged by sshd on every connection, giving
a complete audit trail: which node was accessed, when, and by which certificate.

### Where secrets live

| Secret | Location | Ever transmitted? |
|---|---|---|
| SSH CA private key | RAM-backed volume in controller Pod only — generated fresh on startup, never written anywhere else | Never |
| Ephemeral session private key | Controller memory only, discarded after use | Never written to disk |
| SSH CA public key | ConfigMap in `kube-public` (world-readable, no credentials needed) | Not secret — public key |

The private key never touches etcd, disk, or any Kubernetes Secret. It exists
only in the controller Pod's RAM from the moment it is generated until the Pod
terminates. No operator key management is required.

There is no private key on any node. There is no private key in transit.

### Security properties comparison

| Property | Static shared key | Static per-node keys | SSH CA (this design) |
|---|---|---|---|
| Private key stored on node | ✅ yes | ✅ yes | ❌ no |
| Private key transmitted over network | ✅ yes | ✅ yes | ❌ no |
| Usable from any IP if stolen | ✅ yes | ✅ yes | ❌ locked to controller Pod IP |
| Valid indefinitely if stolen | ✅ yes | ✅ yes | ❌ 10-minute window only |
| Per-session audit trail | ❌ | ❌ | ✅ serial numbers in sshd logs |
| Instant revocation | ❌ must rotate all nodes | ❌ must rotate per node | ✅ replace CA public key |
| Key material to protect | One key (all nodes) | N keys | One CA key (never leaves controller) |
| Node image changes needed to rotate | ✅ yes | ✅ yes | ✅ yes (or cloud-init re-fetch) |

### What an attacker gains by compromising a node

Nothing useful for SSH. The node holds only the CA public key, which verifies
certificates but cannot produce them or reveal the CA private key.

### What an attacker gains by intercepting a session in transit

The ephemeral private key and certificate — but the certificate expires in 10
minutes and the `source-address` constraint means it can only be used from the
controller Pod's IP. A captured certificate is useless from an attacker's
machine even within the validity window.

### What an attacker gains by compromising the controller Pod

The SSH CA private key — they can issue arbitrary SSH certificates to any node
that trusts the CA. This is the single point of failure for the SSH path.

However, this is directly comparable to the existing Kubernetes threat model:
compromising the `kube-controller-manager` Pod today yields the cluster root CA
private key, which allows issuing arbitrary Kubernetes certificates for any
identity in the cluster — a strictly worse outcome. The SSH CA key is scoped
only to SSH access to nodes that have not yet joined the cluster.

Mitigations:
- Run the controller Pod with a hardened `SecurityContext` — see
  [Running the controller Pod securely](#running-the-controller-pod-securely)
- Audit every SSH certificate issuance via the controller's structured logs —
  unexpected issuance patterns indicate compromise
- For the highest security environments, use an external KMS or HSM so the
  CA private key never exists in controller process memory

### SSH CA rotation

Because the controller generates its CA keypair fresh on startup, rotation is
a controller restart:

1. Restart the controller Pod — new keypair generated in memory
2. New CA public key published to `kube-public` ConfigMap automatically
3. Nodes with cloud-init re-fetch the public key on next provisioning
4. All old certificates issued by the previous CA are immediately invalid

No per-node reconfiguration is needed for already-joined nodes — they no longer
accept SSH from the controller after joining (the controller does not SSH into
nodes after CSR approval).

### Relation to the Kubernetes root CA

The SSH CA is a completely separate PKI from the Kubernetes root CA. SSH
certificates use OpenSSH's own certificate format, which is distinct from
X.509. An X.509 intermediate CA cannot directly serve as an SSH CA — they are
different protocols with different certificate structures. Keeping them as
separate PKIs is correct: they serve different trust domains (node SSH access
vs. Kubernetes API authentication) and must be independently rotatable.

### Alternative: agent-based access

In environments where SSH is not available or not desired, the controller can
be extended to support an agent running on each node that exposes a gRPC
endpoint for measurement collection. The agent would authenticate using a
node bootstrap token, providing a node-initiated alternative to SSH.

## CSR Approval and Signing

CSR processing has two distinct steps handled by different components:

1. **Approval** — setting `CSR.status.conditions` to `Approved` or `Denied`.
   Any controller with the appropriate RBAC can do this. The external controller
   handles this step.

2. **Signing** — issuing the actual certificate bytes into `CSR.status.certificate`.
   This is always done by KCM's built-in signer (`kubernetes.io/kube-apiserver-client-kubelet`).
   **No changes to KCM are required** — once a CSR is approved by any approver,
   the KCM signer automatically issues the certificate.

The flow is:

```
External controller sets CSR condition = Approved
         ↓
KCM built-in signer sees Approved → issues certificate bytes
         ↓
kubelet fetches signed certificate → rotation complete
```

The external controller needs only the `approve` verb on the signer — it never
touches certificate issuance.

### Coexistence with the built-in KCM approver

The built-in `csrapproving` controller in KCM auto-approves node CSRs only when
the requestor is a member of the `system:bootstrappers` group. To prevent it from
racing with the external controller, the external controller issues bootstrap tokens
with the group `system:node-bootstrap-controller` instead of `system:bootstrappers`.

The built-in approver ignores this group entirely. No KCM flags or configuration
changes are needed — the two approvers coexist by operating on disjoint sets of CSRs.

**Approval logic (Loop 2):**

```
for each CSR with signer kubernetes.io/kube-apiserver-client-kubelet:
  1. Parse subject CN — must be system:node:<nodeName>
  2. Look up NodeJoinRequest named <nodeName>
  3. If not found → skip (not managed by this controller)
  4. If phase != Verified → deny (controller has not provisioned this node)
  5. If bootstrapExpiry is set and now > expiry → deny, set phase=Expired
  6. Extract public key from CSR
  7. Compare with NodeJoinRequest.status.publicKey
  8. If mismatch → deny, set status.failureReason
  9. If match → approve, set phase=Joined, set status.joinedAt
```

## Required Changes to kubeadm

### `kubeadm join --discovery-mode=wait-for-file`

Currently `kubeadm join` generates `bootstrap-kubelet.conf` itself and fails
if it cannot contact the API server for discovery. A new discovery mode is
needed where kubeadm instead waits for the file to be written externally.

**Proposed flag:**

```
kubeadm join \
  --discovery-mode=wait-for-file \
  --discovery-file=/etc/kubernetes/bootstrap-kubelet.conf \
  --discovery-wait-timeout=30m
```

**Behaviour:**

- kubeadm skips the discovery and kubeconfig generation phases entirely
- Polls for the existence of `--discovery-file` at the given path
- Once the file appears, proceeds with TLS bootstrap as normal
- If `--discovery-wait-timeout` elapses without the file appearing, exits with error

This is a small, focused change to `cmd/kubeadm/app/cmd/phases/join/kubelet.go` —
replace the unconditional write with a conditional that checks for the new mode.

**No other kubeadm changes are required.** The kubelet already honours a
pre-existing key file at `--node-key-file` (or the default path) — if the
controller has written the private key there before kubeadm proceeds, the
kubelet uses it for the CSR without generating a new one.

## Trust Model

| Threat | Mitigation |
|---|---|
| Unknown machine joining | CSR denied — no NodeJoinRequest exists for that node name |
| Stolen bootstrap token used from wrong machine | CSR denied — public key in CSR won't match enrolled public key |
| Node reports fake measurements | Controller verifies over SSH — self-reporting not used |
| SSH session intercepted | Ephemeral key expires in 10 minutes; `source-address` constraint prevents replay from other IPs |
| Node image extracted to find SSH credentials | Node holds only the CA public key — not useful for forging SSH access |
| SSH CA key compromised | Attacker can issue SSH certs to nodes — comparable to KCM compromise which yields the cluster root CA |
| Controller Pod compromised | Attacker can approve arbitrary CSRs — same blast radius concern as KCM today |
| Node joins after bootstrapExpiry | CSR denied — controller sets phase=Expired |
| Same node name joins twice | Second CSR denied — phase is already Joined; admin must explicitly reset |

## Comparison with Existing Bootstrap Token Model

| Property | Bootstrap Token | This Controller |
|---|---|---|
| Any machine can use a stolen token | ❌ yes | ✅ CSR key must match enrolled key |
| Cluster has record of expected nodes | ❌ | ✅ NodeJoinRequest per node |
| Measurements verified independently | ❌ | ✅ controller verifies over SSH |
| Works without CP→node network path | ✅ | ❌ SSH required at join time |
| Works with CAPI | ✅ | ✅ orthogonal to VM creation |
| Certificate rotation re-verified | ❌ | ✅ same key checked on renewal |
| Requires SSH in node image | N/A | ✅ yes |

## Deployment

The controller deploys as a standard Kubernetes Deployment in `kube-system`.

The SSH CA keypair is **generated by the init container on first startup** — no
operator key management required. The private key is written directly into a
RAM-backed volume and never touches etcd. The public key is published to a
ConfigMap (not secret — public keys are safe to store anywhere) so nodes can
be configured with it at image build time or via a DaemonSet.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: node-bootstrap-controller
  namespace: kube-system
spec:
  replicas: 1   # must be 1 — SSH provisioning is not safe to run concurrently
  template:
    spec:
      serviceAccountName: node-bootstrap-controller
      initContainers:
      - name: generate-ssh-ca
        image: node-bootstrap-controller:latest
        command:
        - /bin/sh
        - -c
        - |
          # Generate a fresh ECDSA keypair directly into the RAM-backed volume.
          # Private key: stays in memory only, never written to etcd or disk.
          # Public key: published to a ConfigMap so nodes can trust it.
          ssh-keygen -t ecdsa -b 256 -f /etc/ssh-ca/ca -N "" -C "node-bootstrap-ca"

          # Publish the public key to kube-public so nodes can fetch it
          # without credentials before they have joined the cluster.
          kubectl create configmap node-bootstrap-ssh-ca-pub \
            --from-file=ca.pub=/etc/ssh-ca/ca.pub \
            -n kube-public \
            --dry-run=client -o yaml | kubectl apply -f -
        volumeMounts:
        - name: ssh-ca-mem
          mountPath: /etc/ssh-ca
      containers:
      - name: controller
        image: node-bootstrap-controller:latest
        args:
        - --ssh-ca-file=/etc/ssh-ca/ca
        - --ssh-user=root
        - --ssh-port=22
        - --ssh-cert-ttl=10m
        - --csr-approve=true
        volumeMounts:
        - name: ssh-ca-mem
          mountPath: /etc/ssh-ca
          readOnly: true
      volumes:
      - name: ssh-ca-mem
        emptyDir:
          medium: Memory   # RAM only — never written to node disk
```

**What this achieves:**

- No operator key management — the controller is self-bootstrapping
- Private key is generated in RAM and never touches etcd, disk, or any Secret
- Public key is in a ConfigMap — readable by anyone, not sensitive
- No key to rotate, distribute, or protect outside the controller Pod itself

**On controller restart:**

A new keypair is generated. The public key ConfigMap is updated. Nodes that
have already joined are unaffected — they no longer need SSH access from the
controller. Nodes that were mid-join when the restart occurred will need to
retry; `kubeadm join` with `--wait-for-discovery-file` handles this
automatically since the controller will re-SSH and re-write the bootstrap file
using the new certificate.

The only operational concern is that if node images are built with a specific
CA public key baked in, they must be rebuilt after a controller restart that
changed the keypair. For environments using the DaemonSet-based `sshd_config`
update approach, the new public key is propagated automatically via the
ConfigMap.

**Node image configuration:**

All node images must include the following in `sshd_config`:

```
TrustedUserCAKeys /etc/ssh/controller-ca.pub
```

The CA public key is published to the `kube-public` namespace, which is
world-readable without credentials — the same namespace that holds
`cluster-info`. Nodes fetch it using cloud-init at first boot, using the
API server address they already have from the join command:

```bash
# cloud-init runcmd — runs before kubeadm join
# API_SERVER is the same address passed to kubeadm join
curl -sk ${API_SERVER}/api/v1/namespaces/kube-public/configmaps/node-bootstrap-ssh-ca-pub \
  | jq -r '.data["ca.pub"]' > /etc/ssh/controller-ca.pub
systemctl reload sshd
```

No credentials are needed — `kube-public` ConfigMaps are accessible by
unauthenticated requests. The API server address is always available to
the node before joining since it is a prerequisite of `kubeadm join` itself.

For environments without cloud-init, the public key can be baked into the
node image at build time. In that case a controller restart that generates
a new keypair requires a node image rebuild — treat it as a CA rotation event.

**Future direction: dynamic CA key refresh**

OpenSSH's `TrustedUserCAKeys` directive takes a file path — there is no
built-in equivalent of `AuthorizedKeysCommand` for CA trust. However, a
lightweight agent or cron job on each node could watch the `kube-public`
ConfigMap and refresh `/etc/ssh/controller-ca.pub` automatically whenever
it changes, then send `SIGHUP` to sshd. This would make controller restarts
fully transparent with no image rebuilds needed.

**Required RBAC:**

```yaml
rules:
- apiGroups: [bootstrap.kubernetes.io]
  resources: [nodejoinrequests, nodejoinrequests/status]
  verbs: [get, list, watch, update, patch]
- apiGroups: [certificates.k8s.io]
  resources: [certificatesigningrequests]
  verbs: [get, list, watch]
- apiGroups: [certificates.k8s.io]
  resources: [certificatesigningrequests/approval]
  verbs: [update]
- apiGroups: [certificates.k8s.io]
  resources: [signers]
  resourceNames: [kubernetes.io/kube-apiserver-client-kubelet]
  verbs: [approve]
- apiGroups: [""]
  resources: [configmaps]
  resourceNames: [node-bootstrap-ssh-ca-pub]
  verbs: [get, create, update, patch]
  # Note: this configmap is created in kube-public, not kube-system.
  # A separate RoleBinding scoped to kube-public is required for this rule.
- apiGroups: [""]
  resources: [secrets]
  verbs: [create]   # for bootstrap tokens in kube-system
```

## Operational Workflow

### Adding a node

```bash
# 1. Create the join request (admin, on any machine with kubeconfig)
kubectl apply -f - <<EOF
apiVersion: bootstrap.kubernetes.io/v1alpha1
kind: NodeJoinRequest
metadata:
  name: worker-1
spec:
  nodeIP: 10.0.1.5
  bootstrapExpiry: 2h
  expectedMeasurements:
    kubeletHash: $(ssh root@10.0.1.5 sha256sum /usr/bin/kubelet | cut -d' ' -f1)
    osImageID: ubuntu-22.04
EOF

# 2. Start kubeadm join on the node (waits for discovery file)
ssh root@10.0.1.5 kubeadm join \
  --discovery-mode=wait-for-file \
  --discovery-wait-timeout=30m

# 3. Controller SSHes to 10.0.1.5, verifies measurements, writes credentials
# 4. kubeadm join detects file, completes TLS bootstrap
# 5. Controller approves CSR
# 6. Node appears as Ready
kubectl get nodejoinrequest worker-1
# NAME       PHASE    VERIFIED-AT           JOINED-AT
# worker-1   Joined   2026-05-07T10:01:00   2026-05-07T10:01:45
```

### Re-enrollment after kubelet upgrade

When the kubelet binary is upgraded the `kubeletHash` in `expectedMeasurements`
must be updated before the node's certificate next rotates:

```bash
kubectl patch nodejoinrequest worker-1 --type=merge -p '{
  "spec": {
    "expectedMeasurements": {
      "kubeletHash": "<new-hash>"
    }
  }
}'
```

The controller will verify the new hash on the next certificate rotation CSR.

## Running the controller Pod securely

The controller's single most sensitive asset is the SSH CA private key held in
its RAM-backed volume. Hardening the Pod makes in-process key exfiltration
significantly harder even if an attacker achieves code execution inside the
container.

### Use a minimal container image

The controller is a single statically-linked Go binary (`CGO_ENABLED=0`). It
implements SSH using `golang.org/x/crypto/ssh` — a pure Go library — so no
`ssh` binary, no libc, and no OS packages are needed at runtime.

Build the image `FROM scratch` or `FROM gcr.io/distroless/static`:

```dockerfile
FROM gcr.io/distroless/static:nonroot
COPY --chown=nonroot:nonroot node-bootstrap-controller /node-bootstrap-controller
USER nonroot
ENTRYPOINT ["/node-bootstrap-controller"]
```

With no shell, no package manager, and no external tools in the image, an
attacker with code execution has nothing to pivot with and nowhere to drop
a payload.

### SecurityContext

Apply the following `securityContext` to both the init container and the main
container:

```yaml
securityContext:
  # Run as a non-root UID. The binary must be chowned accordingly in the image.
  runAsNonRoot: true
  runAsUser: 65532      # distroless nonroot UID
  runAsGroup: 65532

  # The only writable path the controller needs is the RAM-backed volume for
  # the SSH CA key. Everything else is read-only.
  readOnlyRootFilesystem: true

  allowPrivilegeEscalation: false

  capabilities:
    drop: ["ALL"]

  # Use the runtime-default seccomp profile, which blocks uncommon syscalls
  # such as ptrace, process_vm_readv, and kernel module loading.
  # For the highest assurance, replace this with a custom allowlist profile
  # that permits only the syscalls the Go binary actually makes.
  seccompProfile:
    type: RuntimeDefault
```

The init container only needs to write to `/etc/ssh-ca` (the RAM volume) and
call the Kubernetes API to publish the ConfigMap. It does not need any Linux
capabilities.

### Pod-level hardening

```yaml
spec:
  # Prevent the service account token from being auto-mounted where not needed.
  # The controller mounts its own projected token explicitly.
  automountServiceAccountToken: false

  # Do not share the host's PID, IPC, or network namespace.
  hostPID: false
  hostIPC: false
  hostNetwork: false

  # Restrict which nodes the controller Pod can be scheduled onto.
  # Prefer control-plane nodes where access is already tightly controlled.
  nodeSelector:
    node-role.kubernetes.io/control-plane: ""
  tolerations:
  - key: node-role.kubernetes.io/control-plane
    effect: NoSchedule
```

### Why a scratch image does not break SSH

A common concern is that removing all OS tooling breaks SSH connectivity.
It does not: the controller makes **outbound** SSH connections using the
pure-Go `golang.org/x/crypto/ssh` implementation compiled into the binary.
There is no `ssh` client binary, no `~/.ssh` directory, and no shell involved.
The SSH protocol logic is entirely inside the statically-linked Go binary.

### Init container as a distroless Go binary

The init container in the Deployment section above uses a shell script that
calls `ssh-keygen` and `kubectl`. This requires a full OS image with those
tools present — which contradicts the hardening goal.

The correct approach is to replace the shell-script init container with a
dedicated, purpose-built Go binary that:

1. Generates the ECDSA P-256 keypair entirely in Go (`crypto/elliptic`,
   `crypto/ecdsa`, `encoding/pem`)
2. Writes the private key PEM to the RAM-backed volume at `/etc/ssh-ca/ca`
3. Uses `client-go` with in-cluster config to `Apply` the `node-bootstrap-ssh-ca-pub`
   ConfigMap in `kube-public`

This binary can be built `CGO_ENABLED=0` and shipped in its own
`distroless/static:nonroot` image:

```dockerfile
FROM gcr.io/distroless/static:nonroot
COPY --chown=nonroot:nonroot node-bootstrap-init /node-bootstrap-init
USER nonroot
ENTRYPOINT ["/node-bootstrap-init"]
```

**Credentials for the init container**

The init container needs to call the Kubernetes API to publish the ConfigMap.
It authenticates using the Pod's ServiceAccount token, which `client-go`'s
`rest.InClusterConfig()` reads automatically from the projected volume at
`/var/run/secrets/kubernetes.io/serviceaccount/token`.

Because the Pod spec sets `automountServiceAccountToken: false`, the token
must be mounted explicitly. Mount it on both the init container and the main
container — both need API access:

```yaml
volumes:
- name: ssh-ca-mem
  emptyDir:
    medium: Memory
- name: kube-api-token
  projected:
    sources:
    - serviceAccountToken:
        expirationSeconds: 3600
        path: token
    - configMap:
        name: kube-root-ca.crt
        items:
        - key: ca.crt
          path: ca.crt

initContainers:
- name: generate-ssh-ca
  image: node-bootstrap-controller-init:latest  # distroless, Go binary only
  securityContext:
    runAsNonRoot: true
    runAsUser: 65532
    readOnlyRootFilesystem: true
    allowPrivilegeEscalation: false
    capabilities:
      drop: ["ALL"]
    seccompProfile:
      type: RuntimeDefault
  volumeMounts:
  - name: ssh-ca-mem
    mountPath: /etc/ssh-ca
  - name: kube-api-token
    mountPath: /var/run/secrets/kubernetes.io/serviceaccount
    readOnly: true

containers:
- name: controller
  image: node-bootstrap-controller:latest       # distroless, Go binary only
  securityContext:
    runAsNonRoot: true
    runAsUser: 65532
    readOnlyRootFilesystem: true
    allowPrivilegeEscalation: false
    capabilities:
      drop: ["ALL"]
    seccompProfile:
      type: RuntimeDefault
  volumeMounts:
  - name: ssh-ca-mem
    mountPath: /etc/ssh-ca
    readOnly: true
  - name: kube-api-token
    mountPath: /var/run/secrets/kubernetes.io/serviceaccount
    readOnly: true
```

**Why the private key still never reaches etcd**

The init container writes the private key only to `/etc/ssh-ca/ca`, which is
the `emptyDir: Memory` volume. That volume is local to the Pod — it is
invisible to the API server and never stored in etcd. Only the public key
travels over the network, as a ConfigMap value, which is not sensitive.

**RBAC for the init container**

The init container uses the same ServiceAccount as the main container. The
existing RBAC rule covering `configmaps` in `kube-public` is sufficient — no
additional permissions are needed. The rule is already scoped to the specific
ConfigMap name via `resourceNames`, so the ServiceAccount cannot read or write
any other ConfigMap in the cluster:

```yaml
# RoleBinding scoped to kube-public namespace
- apiGroups: [""]
  resources: [configmaps]
  resourceNames: [node-bootstrap-ssh-ca-pub]
  verbs: [get, create, update, patch]
```

### Blast radius comparison

| Compromise | What the attacker gains |
|---|---|
| Controller Pod (this controller) | SSH CA key — scoped to SSH access to not-yet-joined nodes only |
| `kube-controller-manager` Pod | Cluster root CA key — can issue arbitrary Kubernetes certificates for any identity in perpetuity |

Running the controller as a hardened distroless non-root container with a
read-only filesystem and dropped capabilities means that exploiting a
vulnerability in the controller binary is substantially harder than exploiting
one in a full-OS container, and the credential exposed is narrower in scope
than what a KCM compromise yields.

## Open Questions

1. **Concurrent SSH provisioning**: replicas=1 is a hard constraint today.
   A leader-election + per-node locking scheme would allow replicas>1 for
   resilience without concurrent SSH to the same node.

2. **Bootstrap token TTL**: the controller creates a bootstrap token to embed
   in `bootstrap-kubelet.conf`. How short should the TTL be? 5 minutes is
   enough for the join to complete but requires the controller to have SSHed
   successfully before starting the clock.

3. **Re-join after node replacement**: if a node is rebuilt (same name, same IP,
   different hardware) the admin must delete and recreate the NodeJoinRequest.
   Should there be a `spec.allowRejoin: true` field that permits re-provisioning
   without deletion?

4. **Agent alternative to SSH**: for environments where SSH is not available,
   define a gRPC interface for the agent-based measurement collection path.
